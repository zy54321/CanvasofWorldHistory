## 三、BAT 03 完整流程

```
双击 <版本>/03_发布Prod.bat
  → cd /d "%~dp0"（包根，不依赖当前目录）
  → chcp 65001
  → powershell -File deploy\publish-prod.ps1

[1/6] 校验 Release 包
  · 目录名与 manifest 版本一致
  · 必需文件齐全（含 publish-prod.ps1 / start-api.bat / flyway.sh / db/migration）
  · SHA256SUMS 全量校验（逐文件比对）
  · jar 与 manifest 记录的 SHA256 一致
  · 迁移文件最高版本 = manifest.database.targetFlywayVersion
  · 包内无 .env / 私钥 / dump
  · 目标版本目录不存在（尽早失败，不依赖数据库）

[2/6] 识别当前生产环境
  · 读 PROD/current.json（不存在 → legacy_unversioned，不伪造历史版本）
  · 数据库容器健康状态必须为 healthy
  · 生产配置 PROD/config/.env（不存在则从现有容器读取凭据生成，仅首次）
  · 连库校验 current_database() == 目标库名，不符立即停止
  · 读取 flyway_schema_history 最高版本
  · 检查目标端口占用

[3/6] 变更摘要
  · 当前版本 / 目标版本 / 数据库版本迁移方向
  · 数据库版本高于包要求 → 拒绝（不支持降级）

[4/6] Y/N 确认部署

[5/6] 数据库迁移（仅当 DB 版本 < 目标版本）
  · 一次性 pg_dump 保护（非正式备份体系）
  · Y/N 二次确认
  · flyway migrate（只正向，无 clean、无重建）
  · 迁移后复核版本号

[6/6] 部署与切换
  · 复制包内容到 PROD/<版本>/（api、deploy、docs、manifest、SHA256SUMS、web）
  · 生成 web/config.js（MapTiler key 运行时注入，jar 不重构建）
  · 复制后复核 jar SHA256
  · 临时端口（默认 5199）启动验证 + health 检查
  · 目标端口被占用时显示进程并要求 Y/N 确认后才停止
  · 正式端口启动 + health（校验 database 字段）
  · 冒烟：/meta/stats、/places?keyword=Roma

[收尾]
  · 写 current.json（原子写，无 BOM）
  · 首次部署写 legacy-unversioned/legacy-record.json
  · 写 logs/deploy-<时间戳>.log
  · 失败时绝不写成功的 current.json
```

**BAT 03 不存在的行为**：重新编译、修改包内产物、Flyway clean、重建数据库、自动数据库回滚、覆盖历史版本目录。

## 五、施工中修掉的问题（6 个）

| # | 问题 | 影响 | 处理 |
|---|---|---|---|
| 1 | **PowerShell 5.1 `Start-Process` 环境块大小写冲突** | 本机同时存在 `HTTPS_PROXY` 与 `https_proxy`，启动任何子进程都抛 `Item has already been added`，部署完全无法进行 | 脚本启动前删除小写代理变量（仅当前进程，关闭窗口即恢复） |
| 2 | 尝试绕开 #1 改用 `ProcessStartInfo.EnvironmentVariables` | 该属性在当前 PowerShell 会话返回 null，索引即报 `Cannot index into a null array` | 放弃该方案，回到 Start-Process |
| 3 | `Get-ChildItem Env:` 枚举本身也因重复键抛异常 | 无法用枚举方式清理 | 改为按已知变量名逐个 `Remove-Item` |
| 4 | `Invoke-WebRequest` 进度条污染输出 | 部署输出被大量 "Reading web response" 噪音淹没 | 脚本开头 `$ProgressPreference = 'SilentlyContinue'` |
| 5 | `-DryRun` 无 config 时误判库名不符 | 只读校验永远失败 | 只读时从容器 `docker inspect` 读取身份，跳过配置文件断言 |
| 6 | "目标版本已存在"检查位置太靠后 | 要连完数据库才发现重复，浪费且掩盖真实原因 | 提前到包校验之后、连库之前 |

第 1 个是环境级的硬阻塞，花了最多时间定位：`Start-Process` 与 `Get-ChildItem Env:` 两条路都被同一个根因堵死，最后靠"删除已知重复变量"绕过。

## 六、BAT 02 两处衔接问题修正

### 问题 A：BAT 03 必须进入 Release 包 —— 已修正

模板收集从 4 个文件扩展到 6 个，并把 `03_发布Prod.bat` 单独放到包根：

```powershell
foreach ($t in @('docker-compose.prod.yml','start-api.bat','start-api.sh','flyway.sh','publish-prod.ps1')) {
    Copy-Item ... (Join-Path $pkg 'deploy')
}
Copy-Item (Join-Path $tplDir '03_发布Prod.bat') -Destination $pkg
```

`$required` 清单同步加入 `03_发布Prod.bat` 与 `deploy/publish-prod.ps1`，缺失即构建失败。

**验证**：生成包后 `find` 确认包根有 BAT，`deploy/` 有 ps1；包内没有任何指向 DEV 目录的引用（BAT 用 `%~dp0`，ps1 用 `$PSScriptRoot` 上溯）。

### 问题 B：Tag 与归档一致性 —— 已修正

原顺序：`归档 → 询问 Tag → 创建 Tag`。用户取消 Tag 时，正式目录里已经躺着一个"没有 Tag 的包"。

新顺序：**先 Tag，成功后归档**。

| 分支 | 行为 |
|---|---|
| 取消创建 Tag | 清理临时构建目录，正式目录不留任何东西，exit 0 |
| Tag 创建失败 | 不归档，exit 1 |
| Tag 成功但归档失败 | 删除目标目录 + `git tag -d` 回退，避免"有 Tag 无包" |
| Tag 成功、推送失败 | 包与本地 Tag 都在，明确提示"未推送状态"，exit 1（不伪装成功） |
| `-SkipTag` | 直接归档，并明确警告"该包不是正式 Release" |

**验证**：T10 确认取消 Tag 后目录数与 Tag 数均不变；T11 确认版本来源不一致时不做任何归档。
