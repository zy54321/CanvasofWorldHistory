## 四、历史数据资产性质认定（§3.4）

### 4.1 事件（`m2check` 32 条）

| 类别 | 条数 | 判定依据 |
|---|---:|---|
| `演示：*`（马拉松、温泉关、秦灭六国…） | 12 | 标题自带"演示："前缀；2026-11-04 09:29 一次性批量创建 |
| `测试*` / `孔子适周问礼` / `测试-跨前后事件` | 20 | 同一条内容被重复创建 4–6 次（id 1/65/72/78/81/85 完全相同），是接口/UI 回归的夹具 |

**全部 `created_by='manual'`、`record_status='staging'`、`created_at` 均为 2026-11-04（当天验收期间）。**
结论：**没有一条可以认定为正式历史业务数据。** 其中"孔子适周问礼"史实成立，但它是作为测试用例被创建 6 次的，
不能凭"内容真实"就当成人工整理成果。

### 4.2 人物（20 条）与政权（8 条）

同样全部 `created_by='manual'` / `record_status='staging'`，与 12 条演示事件一一配套（演示事件引用的政权与人物）。
性质：**M2/M3 验收夹具**。

## 五、两套库之间的差异是否"无法解释"（§八 停止条件核查）

`canvas_history` 与 `m4check` 行数完全相同但 `place_id` 区间不同（19,046–38,084 vs 1–19,039），
说明 `m4check` 是**重新导入**出来的、不是克隆，两库的主键空间天然不同。

按自然键 `(dataset_id, grain_key)` 逐行比对（剔除 `place_id`、`created_from_source_record_id`、`updated_at`）：

| 结果 | 数量 |
|---|---:|
| 内容相同 | 19,037 |
| 内容不同 | **2**（`whg_hgis_de_las_indias_sample` 的 `169687` 与 `169687-169688`） |

这 2 条正是 `m4check` 多出的 2 行 `attribution_missing` 台账对应的地点：M4-2 把"授权信息"从准入门槛
降为可选溯源后，`notes` 里多了一句 `source_flags=attribution_missing`。**差异可解释、不涉及人工数据、不涉及业务丢失。**

其余 13 个库与本轮无关（V3 阶段库、故障空库、测试副本），未发现来源不明的数据。

## 六、Pleiades 地点名称专项审计（§3.5）

对 `m4_5_verify` 的 57,967 个地点做了全量分类：

| 分类 | 数量 |
|---|---:|
| 有有效名 + 有坐标 | 45,921 |
| 有有效名 + 无坐标 | 8,126 |
| **无有效名 + 有坐标** | **3,778** |
| **无有效名 + 无坐标** | **142** |
| 合计 | 57,967 |

"无有效名"= `canonical_name` 为空、纯空白，或命中占位名集合。实测 **没有空值、没有纯空格**，
3,920 条全部是**源里的占位标题**：

| 占位标题 | 条数 | 说明 |
|---|---:|---|
| `Untitled` | 3,837 | Pleiades 对无正式名称遗址的固定标题 |
| `Unnamed Place` | 58 | 同上，另一种写法 |
| `Unnamed place` | 25 | 同上，大小写变体 |

进一步核查：

- **64 条**（全是 `Untitled`）**有可替代的真实别名**，例如 `145174` → "Labastide-d'Armagnac"、
  `145188` → "Jurançon"。这些地点应当显示其名称行，而不是 `Untitled`。
- **3,856 条完全没有任何名称行**（`name_rows = 0`），原始 `places.csv` 的 `title` 也是占位值，
  `names.csv` 里没有对应记录 —— 不是导入丢失，是源本来就没有名字。
- 3,778 条有坐标，会以"无名点"出现在地图上。

明细见 `ops/reports/p0/name_audit.csv`（3,920 行，含 place_id / grain_key / 坐标 / 源记录 / 关联名称）。

> 这不是 M4 导入的缺陷，是 Pleiades 数据本身的形态。但它确实违反"没有有效地名的地点不能作为正常命名地点展示"，
> 需要在展示层处理（见 §八 决策 C）。

## 八、需要 Owner 确认的三项决策（第三阶段执行前提）

### 决策 A：权威库与升级路径（建议：按演练方案执行）

- 权威库定为 **`canvas_history`**，保持其全部主键与关联不变；
- 在其上执行 **V6 → V7 → V8 → V9**（文件与 checksum 已核对一致）；
- 用 **`data/staging_m4_5`**（哈希已验证）执行一次幂等导入；
- 预期结果 = 演练库：57,967 地点 / 157,220 源记录 / 66,311 候选 / 20,824 台账，既有 6 表指纹不变。

风险与回滚：升级前对 `canvas_history` 做一次 `pg_dump` 全量备份（167 MB），失败即删库从备份恢复。
不做整表覆盖、不做 `INSERT SELECT *`。

### 决策 B：事件 / 人物 / 政权是否保留空态（建议：保持空）

全库无真实数据，按规则不应把 12 条演示 + 20 条测试事件迁入正式库。
后果：**M3 的时间轴事件气泡、时空矩阵内容、事件详情在权威库上会是空的**（矩阵有内置空态文案，不算报错）。

如果 Owner 希望正式库里能看到演示内容，需要明确授权"把演示数据集作为独立 dataset 导入并标注为 demo"，
这属于新增业务语义，我不擅自做。

### 决策 C：3,920 个占位名地点如何展示（建议：只改展示层，不改数据）

建议三条一起做，都只在读取侧生效、不写库：

1. 若 `canonical_name` 是占位名**且**该地点有名称行 → 显示名称行的文本（64 条，例如 `Untitled` → "Jurançon"）；
2. 若没有任何名称行 → 显示"未命名遗址 · #`grain_key`"并加弱化标记，**不冒充历史地名**；
3. 接口新增布尔字段 `nameIsPlaceholder`，前端据此显示标记；`canonical_name` 原值保留不动。

需要确认的点：**是否允许我为此修改后端 4 处 SQL 读取点 + 1 个 DTO 字段 + 1 处前端展示**（约 +60 行）。
若要求"质量问题必须进 `data_quality_issue` 台账"，则要改 `normalize.py` 并**重建暂存**（等同再做一次 M4-5 级改动），
成本明显更大，建议留到下一轮。
