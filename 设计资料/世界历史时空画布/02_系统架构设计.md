# 02｜系统架构设计（V1.0）

## 1. 技术路线

| 层次     | 选型                 | 说明                                       |
|:---------|:---------------------|:-------------------------------------------|
| 前端     | Vue 3 + TypeScript   | 页面、时间轴、对象管理和交互               |
| 地图渲染 | MapLibre GL JS       | 底图渲染与历史图层                         |
| 地图供应 | MapTiler Cloud       | Outdoor、Streets、Satellite、Hybrid 等样式 |
| 后端     | Spring Boot          | 模块化单体、REST API、数据导入             |
| 数据库   | PostgreSQL + PostGIS | 关系数据和空间数据                         |
| 部署     | Docker Compose       | Web、API、DB 独立容器                      |

## 2. 地图适配

地图业务模块不得把 MapTiler 的具体 style URL、token
拼接和供应商细节散落在业务组件中。

建议设置统一地图配置与适配边界： -
`MapProviderConfig`：地图供应商配置。 -
`MapStyleRegistry`：可用样式清单和默认样式。 -
`MapViewState`：中心点、缩放级别、当前样式等视图状态。 -
历史信息图层通过项目 API 获取，不依赖 MapTiler 的业务数据结构。

V1 只接入 MapTiler，但保持替换供应商时不需要改动地点、人物、事件模块。

## 3. MapTiler 凭证要求

- 浏览器地图加载需要使用可公开但受限的 API key。
- API key 必须在 MapTiler 控制台限制 Allowed HTTP origins。
- `VITE_` 前缀环境变量构建后会进入浏览器，不能当作服务端秘密。
- Service token 等服务端秘密不得进入浏览器、Git、日志、截图或文档。
- 不在交接包中保存任何真实 key/token。
- 保留 MapTiler 要求的 attribution。
- WorkBuddy
  不应要求用户在聊天消息中粘贴凭证；应指导用户在本地环境文件中配置。

## 4. 前端模块建议

``` text
src/
  app/
  modules/
    map/
    timeline/
    place/
    person/
    event/
    search/
    data-source/
  shared/
    api/
    components/
    composables/
    types/
    utils/
```

模块职责： - `map`：地图实例、样式切换、视野状态、历史图层、聚合。 -
`timeline`：BCE/CE 转换、年份输入、时间范围选择。 -
`place`：地点管理和地点详情。 - `person`：人物档案和人物观察。 -
`event`：事件管理和关联维护。 - `search`：跨对象搜索。 -
`data-source`：来源信息和导入状态展示。

避免过早引入复杂状态管理。先用 Vue composables
和模块内状态；确有跨模块复杂状态需求时再引入 Pinia。

## 5. 后端模块建议

``` text
backend/
  modules/
    place/
      api/
      application/
      domain/
      infrastructure/
    person/
    event/
    source/
    dataimport/
  shared/
    config/
    exception/
    persistence/
```

使用模块化单体：一个 Spring Boot 应用，内部按业务模块组织。模块间通过
application/service 接口交互，不直接跨模块操作对方 Repository。

## 6. 数据库

- PostgreSQL + PostGIS。
- 业务空间数据统一使用 WGS84 / EPSG:4326。
- 空间字段建立 GiST 索引。
- 常用时间字段建立 B-tree 索引。
- 数据库 schema 通过版本化 Migration 管理。
- 数据库版本和 PostGIS 版本固定，不使用 `latest`。
- 原始导入文件与正式业务数据分开存放。

Migration 工具可以在正式施工前从 Flyway / Liquibase
中选一个轻量方案，不要两者并用。

## 7. API 原则

建议以 `/api/v1` 为前缀。

主要能力： - `GET/POST/PATCH/DELETE /api/v1/places` -
`GET/POST/PATCH/DELETE /api/v1/persons` -
`GET/POST/PATCH/DELETE /api/v1/events` -
`GET /api/v1/map/events?fromYearAstro=&toYearAstro=&bbox=` -
`GET /api/v1/map/places?bbox=&year=` -
`GET/POST/DELETE /api/v1/events/{id}/places` -
`GET/POST/DELETE /api/v1/events/{id}/persons` -
`GET/POST/DELETE /api/v1/persons/{id}/places` -
数据源和导入批次查询接口。

地图接口按当前
bbox、时间范围和筛选条件查询，不向浏览器一次性返回全量历史数据。

事件时间区间与当前观察区间有重叠时，应返回该事件。若事件没有可定位地点，则返回列表数据但不生成地图标记。

## 8. 部署与安全

- Docker Compose 管理 web、api、db。
- 数据库使用持久化 volume。
- 导入原始文件使用宿主机挂载目录或独立 volume。
- 提供 `pg_dump` 备份和恢复说明。
- V1 默认本地个人使用；在 Owner 未确认前，不进行公网部署。
- 端口默认绑定 localhost；如需局域网访问，再单独配置。
- 不引入 Redis、Elasticsearch、Neo4j、GeoServer、Kafka
  或微服务，除非有经过证明的实际需求。

## 9. 性能原则

- 地图首屏先显示底图，不等待历史数据全部加载。
- 按时间范围和 bbox 加载历史数据。
- 低缩放级别采用聚合。
- 详情按需加载。
- 数据导入分批处理，不使用超大单事务阻塞查询。
- 样式切换保留地图视野和当前时间状态。
