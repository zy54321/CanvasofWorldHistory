> ⛔ **哨兵 `'-'` 的强度**：它是**值域外保留字**，只能在 `data_dataset` 或一张常量表里**声明一次**（C29 ④）。若将来某数据集的 parent 恰为 `'-'` ⇒ 换哨兵是一次性常量替换，**不得牵动五段键逻辑**。

> ⛔ **三张视图的 SQL 必须是可编译的完整 SQL，不得出现占位符或引用视图不存在的列。** 本轮已修掉三类回归（§E.1 的占位符与写死 `FALSE`、§E.2 的缺 `JOIN`、§E.3 的裸 `count(*)`）。**下轮若要从权威设计（V0.2.2）重新抄视图，必须先核这三条**——V0.2.2 §2.2.2 / §2.2.4 自身含这些缺陷，照抄即复发。

## E.1 `v_place_evidence`（**11 列**；`is_canonical_row` 由外层窗口定序计算）

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | **V2.1 无此视图**。V0.2.1 定为 4 列；V0.2.2 §2.2.2 的 SELECT 实为 11 列，但 §6 第 3 项（行 1052）写"**10 列**"，且 creator 分支写死 **`FALSE AS is_canonical_row`**、② 分支留 **`<canonical 定序 §5.10.4>` 占位符**（**不可执行**）。 |
| **修改后（V2.1.1）** | **11 列**（逐列见下表）；`is_canonical_row` **由外层窗口函数 `row_number() OVER (PARTITION BY place_id ORDER BY …) = 1` 实际计算**，三支 `UNION ALL` 整体下沉为子查询 `u`，涉及 `duplicate_ordinal` / `external_id` 的定序键一律**回连 `source_record`**取值。**creator 行也可能为 `true`**——315 个无子行地点靠此追溯。 |
| **原因** | ① **旧写法自相矛盾**：creator 分支写死 `FALSE`，却又要求"315 个无子行地点的 `is_canonical_row=true` 落在 creator 行"——两者不可能同时成立；② **定序键不在视图里**：`duplicate_ordinal` / `external_id` 是 `source_record` 的列，**任何"在视图内直接 ORDER BY 这两列"的写法都不可执行**；③ **`place_record` 与 `creator` 同名异义**必须收敛为 3 值。 |
| **影响** | 视图：本身；下游：`v_place_liveness` 的 CTE 源、`DATA_PROVENANCE` 的追溯通路、`IMPORT_RULES` §10 的 canonical 计算；文档：CORE §5.10.1/§5.10.4/§5.10.5。 |
| **验证状态** | **结构已验证**（SQL 可编译；占位符与写死常量**共 3 处全部消除**：creator 分支 `FALSE` 1 处、location 分支 `FALSE` 1 处、name 分支占位符 1 处）。**未验证**：① 315 个无子行地点的 canonical 是否**全部**落在 creator 行；② MCGD 643 个按组地点是否落到最小 `NameID`；③ 同记录多行 name 时 canonical 是否确定性唯一（同输入两次查询结果必须相同）——=`V-8`。 |
| **出处** | V0.2.2 §2.2.2（行 190–220）、§2.8.2（行 816）、§6-3（行 1052）；V0.2.1 §2.4.2；CORE §5.10.1、§5.10.4。 |

**列清单（11 列，逐列）**

| # | 列 | 类型 | 说明 |
|---:|---|---|---|
| 1 | `place_id` | bigint | |
| 2 | `source_record_id` | bigint | |
| 3 | `evidence_role` | text | **3 值** `creator` / `name` / `location`。⛔ `place_record` 是**禁用词** |
| 4 | `source_is_active` | boolean | 派生 |
| 5 | `source_inactive_reason` | text | 派生 |
| 6 | `child_table` | text | `'name'` / `'location'` / NULL（creator 行为 NULL） |
| 7 | `child_row_id` | bigint | 派生 |

| 11 | `is_canonical_row` | boolean | **三支统一由外层 `row_number()` 计算**。⛔ 不再是写死常量、也不是占位符 |

**定序键（写死，顺序不可换）**

```
⓿ (source_is_active AND child_record_status IS DISTINCT FROM 'rejected') DESC  -- 有效证据优先
① (evidence_role = 'creator') DESC                                            -- 创建记录优先
② sr.duplicate_ordinal ASC NULLS LAST                                         -- 与 §4.3 同源（回连 source_record）
③ sr.external_id       ASC NULLS LAST                                         -- MCGD 即"NameID 最小"（回连 source_record）
④ source_record_id     ASC                                                    -- 破并列（可复现）
⑤ coalesce(child_row_id, 0) ASC                                               -- 同记录多行 name 的行级破并列（可复现）
```

> **两个补全项（不是新设计，登记 `V-8` 待 QA 复算）**
> - **⓿ 不可省略**：定义句写的是"本地点**有效证据**中定序第一的行"。缺 ⓿ 时，一条 `rejected` 子行或失效源行可能排到有效证据之前成为 canonical ⇒ **视图语义与定义句自相矛盾**。
> - **⑤ 不可省略**：C08 允许一条 `source_record` 派生**最多 3 行 name**（`name_type` 不同），其 ②③④ 键**全同**；缺 ⑤ 则并列行的 `row_number()` 取值**不可复现**。
> **零有效证据的地点**：`is_canonical_row` 仍会落在一行（"最佳可得"），**仅用于追溯，不代表该行有效**；该地点的 `liveness` 必属 `FAILURE_SET` 或 `orphaned`。**`DATA_PROVENANCE` 必须写明"canonical ≠ 有效"。**
> **join 条件的"旧用法作废"声明**：V0.2.1 §2.4.2 原写法里的 `AND sr.record_scope <> 'place'` **已作废**——它把 `edge` 与未来任何新类型**默认放行**，被 §2.7 白名单取代。
> **锚点 vs 当前最佳证据**：`created_from_source_record_id`（锚点，IDENTITY，**永不改写**）与 `is_canonical_row`（当前最佳证据，**每次导入重算**）指向不同记录**不是错误**，不落台账。

| **修改后（V2.1.1）** | `liveness` **8 值**（新增 `mixed_inactive`）；`ev` CTE **必须 `JOIN source_record sr ON sr.source_record_id = e.source_record_id`** 取 `inactive_at` / `inactive_in_batch_id`；**对外 7 列**（`place_id` / `dataset_id` / `grain_key` / `record_status` / `manual_rejected_rows` / `distinct_inactive_reasons` / `liveness`）。 |

| **影响** | 视图：本身；`GROUP BY` **不变**（`sr.inactive_at` / `sr.inactive_in_batch_id` 只出现在聚合函数内部，`source_record_id` 是 `source_record` 的主键 ⇒ 功能上依赖 `e.place_id`，`GROUP BY e.place_id` 仍充分）；断言：R4a–R4f、C27/C28；文档：CORE §5.10.2、DATA_PROVENANCE §7.2。 |
| **验证状态** | **结构已验证**（补 JOIN 后 `ORDER BY` 两列真实存在；`SELECT` 的省略号已按 V0.2.2 §2.1.2 / §2.2.3 / §2.2.5 与 V0.2.1 §2.3.4 补全，属**补全项**）。**未验证**：建视图后能否真正编译、`GROUP BY` 的功能依赖是否被数据库接受——=`V-9`/`V-1`。 |

**`liveness` 8 值的派生优先级（自上而下，命中即返回，顺序不可换）**

| 序 | 判据 | `liveness` | 类别 |
|---:|---|---|---|
| 1 | `record_status = 'merged'` | `merged` | 合并态 |
| 2 | `created_by = 'manual'` | `manual` | 有效态（永不失效） |
| 3 | ∃ 有效证据 | `active` | 有效态 |
| 4 | 证据全失效，原因**唯一** = `source_absent` | `all_sources_absent` | 来源失效态 |
| 5 | 证据全失效，原因**唯一** = `batch_rolled_back` | `all_sources_rolled_back` | 批次回滚态 |
| 6 | 证据全失效，原因**唯一** = `duplicate_quarantine` | `quarantined_only` | 隔离态 |
| 7 | 证据全失效，原因 **≥2 种** | **`mixed_inactive`**（本版新增） | 混合失效态 |
| 8 | 证据集为空，或有失效但原因缺失 | `orphaned` | 孤立态（非法终态，断言 = 0） |

**真值表（`liveness` × `record_status`，✅ = 唯一合法组合）**

| `liveness` | `staging` | `rejected` | `merged` |
|---|---|---|---|
| `active` | ✅ | ❌ | ❌ |
| `manual` | ✅ | ❌ | ❌ |
| `merged` | ❌ | ❌ | ✅ |
| `all_sources_absent` | ❌ | ✅ | ❌ |
| `all_sources_rolled_back` | ❌ | ✅ | ❌ |
| `quarantined_only` | ❌ | ✅ | ❌ |
| `mixed_inactive` | ❌ | ✅ | ❌ |
| `orphaned` | ❌ | ❌ | ❌（**唯一允许 0 个 ✅ 的行**） |

**`FAILURE_SET = {all_sources_absent, all_sources_rolled_back, quarantined_only, mixed_inactive}`；`rejected ⟺ liveness ∈ FAILURE_SET`。**

> **`(manual, merged)` 取 ❌ 的理由**：优先级第 1 行（`merged`）在第 2 行（`manual`）**之前**命中 ⇒ 该格**永远不可达**。保留 ✅ 会让表头自相矛盾，并诱导实现者写出"先判 manual 再判 merged"的代码（与本设计相反）。信息不丢失——"人工地点可被人工合并"由 `merged` 行表达；`manual` 行语义退化为"人工创建且未被合并"。
> **⚠️ "8 值"与"7 列"不是一回事（W-04 澄清）**：标题的「8 值」指 `liveness` **列的枚举值个数**；「7 列」指**本视图对外输出的列数**。**枚举值个数 ≠ 列数，两者不矛盾。**
> **⚠️ 口径修正（QA F-04）**：本节旧稿标题写「9 列」，但表内只编号 1–7、SQL `SELECT` 也只输出 7 列 ⇒ **标题与实体自相矛盾**。本版按**方案 A（SQL 不动）**统一为 **7 列**；`has_valid` / `reasons` 明确为 **CTE 中间量、不计入对外列**；`last_inactive_reason` 已被 `reasons` 数组取代、**不对外**。「对外新增 2」与「对外总列数 7」是**两个不同口径**，不冲突。

**四条不变式（施工后逐条验，必须 0 违反）**

```
T1  from_evidence_rows = 0 ⇒ span_from_astro IS NULL
T2  to_evidence_rows   = 0 ⇒ span_to_astro   IS NULL
T3  span_from_astro > span_to_astro 的行数 == 0（倒挂的 28 条在子行上已留空）
T4  derivation_kind 三值计数 == 1,570 / 361 / 17,108（合计 19,039，暂存态干跑）
    且 count(derivation_kind='single_point' AND span_from_astro IS NULL) = 0
```

**新增断言 T5（三项豁免）**

```
T5  count(place WHERE liveness='active'
                 AND derivation_kind='no_evidence'
                 AND NOT ( child_rows_total = 0
                        OR all_children_rejected
                        OR ( valid_child_rows > 0
                             AND 全部有效子行的 f 与 t 皆为 NULL ))) == 0
```

> **T5 的有效命中率必须写清，避免高估断言价值**：暂存态干跑中"被过滤"情形 **0 例**，T5 抓到的 1,255 个**全是"本来没有"**。**T5 在真实数据上 0% 有效命中**——它是**防未来回归的护栏**，不是当前的缺陷探测器。三项豁免后干跑 **T5 = 0**。

## F.1 判定表：10 行 → **11 行**（新增第 0 行「重复检测优先」）

## F.2 重复隔离算法（写死；四种排列的隔离数是**验收判据**）

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | **未写死判据**。只说"重复外部 ID 隔离"，第 2 条被业务唯一键挡下后记 `duplicate_external_id` + `action_taken='rejected'`（**REJECT**，不是隔离）。 |
| **修改后（V2.1.1）** | 见下方判据块 + 四排列推演。处置是 **QUARANTINE**（`is_active=false` + `inactive_reason='duplicate_quarantine'`），**不删行、不派生子行**。 |
| **原因** | ① **REJECT 会让源记录在库里不存在**，`raw_payload` 这份原始证据一起消失；② 判据不写死则实现者必然写出"只比 `ordinal=1` 的 hash"或"要求整组内容完全相同才隔离"两种错法——**后者会直接漏掉 `sr_0027175`**（`pleiades_connection_id / 20469` 是**混合组**：3 行里 2 行相同、1 行不同）。 |
| **影响** | `source_record`（3 条 `is_active=false`）；子行（name −4 / location −2）；`data_quality_issue`（+5 条 `duplicate_external_id`）；第 0 行；STOP_AUTO 的判据（同一个多重集机制，**一处实现、两处语义**）。 |
| **验证状态** | **已验证（真实数据复算）**：3 条隔离，`record_scope='place'` 18,398 − 2 = **18,396** = 19,039 − 643 ✓；四种排列的隔离数与真实混合组逐格推演一致（见下表）。**未验证**：隔离行在建库后"不派生任何子行"（=`S1`）。 |
| **出处** | V0.2.2 §2.3、§2.5.0（行 562–564）；V0.2.1 §2.5.3；IMPORT_RULES §5.1–§5.4；CORE §4.3、§4.6。 |

**判据（写死）**

```
对四段前缀 g 的组内每一行 r，按 (content_hash ASC, raw_record_index ASC) 定序后：
  · 同一 hash 子组内【最小 ordinal】保留
  · 该子组内后续相同 hash 的行 ⇒ 隔离（is_active=false, inactive_reason='duplicate_quarantine'）
  · 不同 hash 的行 ⇒ 均保留（不隔离）
```

⛔ **禁止"只比 `ordinal = 1` 的 hash"**。
⛔ **禁止"要求整组内容完全相同才隔离"**。

**四种排列 + 真实混合组（隔离数即验收判据）**

| 排列 | 定序后 | 保留 | 隔离 | **隔离数** |
|---|---|---|---:|
| `A,B,B`（3 行） | A,B,B | 1(A)、2(B) | 3(B) | **1** |
| `B,A,B`（仅文件顺序不同） | A,B,B | 1(A)、2(B) | 3(B) | **1** |
| `A,B,C`（三个不同 hash） | A,B,C | 全部 | — | **0** |
| `A,A,B,B`（4 行） | A,A,B,B | 1(A)、3(B) | 2(A)、4(B) | **2** |
| `A,A,B`（真实混合组 `98909/20469`） | A,A,B | 1(A)、3(B) | 2(A) | **1** ← `sr_0027175` |

> **`A,B,B` 与 `B,A,B` 结果逐位相同**——这正是设计目标：**ordinal 不受行序影响**。物理顺序只在 `content_hash` 相等时经 `raw_record_index` 破并列，而并列行内容不可区分 ⇒ 无语义影响。
> ⭐ **`A,A,B,B` 的易错点（经 team-lead 裁定更正）**：「不同 hash 记录均保留」指的是**跨子组**（B 组不会因为与 A 组 hash 不同而被隔离）——但**子组内部仍要执行"最小保留、后续隔离"**：B 出现两次，第二次**照样要隔离**。否则两个内容相同的 B 会同时入库，**去重就失效了**。先前写的"只隔离第二个 A、两个 B 都保留"**是错的**，它等价于被明令禁止的旧规则。
> **"隔离"不是"删除"**：`is_active=false` + 三列 `inactive_*` 完整保留，原始行与原因都在（C21/C22）。

## F.3 建点白名单：`record_scope <> 'place'` → **白名单 + `place_grain` 显式声明**

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | 建点判据写 `record_scope <> 'place'`（**过宽**）：凡不是 place 的记录都可能被当作建点依据，`edge` 与未来任何新类型**默认放行**。 |

| **出处** | V0.2.2 §2.7.1–§2.7.3；V0.2.1 §2.4.2；CORE §5.5.5、§5.2.2；IMPORT_RULES §4。 |

V3'  count(creator 证据行 WHERE is_anchor) == 19,039        -- 每地点恰好 1 条锚点（入库口径）

## F.4 地点解析：三种结局，没有第四种

| 结局 | 条件 | 动作 |
|---|---|---|
| **命中** | 地点已存在（本批已建或库中已有） | 正常挂子行 |
| **新建** | `place_grain='per_parent_external_id'` 且地点不存在 | 建地点（MCGD：960 条 name → **643** 个地点） |
| **孤儿** | `place_grain='per_record'` 且地点不存在 | **不建地点**；落 `parent_place_not_in_sample`（info / preserved_and_flagged）；`source_record` **仍入库且 `is_active=true`** |

> **孤儿记录为什么必须留着**：那 4,810 条是**真实的源数据行**，只是父地点不在这批切片里。下一批全量导入时，同一个五段键会命中已有记录，届时地点出现、子行自动补齐。**删了它们，全量导入时会漏掉这 4,810 条。**
> **Pleiades 的切片代价（不是数据质量问题）**：4,579 条 name 记录只产出 **2,074** 行名称、2,460 条 location 记录只产出 **1,704** 行位置。差额（2,505 + 756）= "父地点不在切片内"（切片按 `places.csv` 前 2,643 行截断）。这类记录**不入库**（否则会造出没有地点的孤儿名称），全部记 `parent_place_not_in_sample`。
> **数据集内部写入顺序**：**place-scope 优先**（V2.1 未规定）。若先导 `names.csv`，4,579 条名称里凡父地点在切片内的都会变成孤儿——**不会报错**，只会让 `parent_place_not_in_sample` 从 4,810 暴涨到 9,000 以上，然后被当成"切片太小"解释过去。

## F.5 回滚：两组集合与两条恒等式

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | 回滚统计只写"`\|B\| − blocked_count`"，**两组计数混用同名**（`N_fail` / `N_quar` / `N_blocked` / `N_noop` 在导入语境与回滚语境各指一物），且 R1 的右式**漏减 `N_noop`**、**漏减 `N_quar`**。 |
| **修改后（V2.1.1）** | 两组集合**互斥且穷尽**，恒等式写死如下；`N_failed` **从此不带下标不使用**（写作 `N_fail_import` / `N_fail_rb`）。 |
| **原因** | ① **同名不等于同集**：`N_quar` 在 G1 指"本批新产生的隔离行"，在 G2 指"`B` 中处于隔离态的行"（可能是被回滚批产生的，也可能是**后续批次**重判产生的）；② **`N_noop` 是致命项**：G2 的 `N_noop` 若判定顺序错，会把 `N_quar` 截走（洞 4）；③ 漏减任一项 ⇒ 恒等式不成立 ⇒ 有人会"为了配平改语义"。 |
| **影响** | ROLLBACK §3、§5；IMPORT_RULES §7.4；`import_batch.blocked_count`（本轮新增列）；判定顺序（F.6）。 |
| **验证状态** | **结构已验证**（六集合两两不相交、任一输入行结局只有 6 种；4 格穷尽表 3 格合法 + 1 格不可能）。**未验证**：真实回滚批次的端到端行为（=`U5`，暂存态 `rejected` / `merged` / `locked` 均 **0 条**，无数据可验）。 |
| **出处** | V0.2.2 §2.4.1–§2.4.3（行 509）；V0.2.1 G3-04（行 336）；ROLLBACK §3、§5；IMPORT_RULES §7.4。 |

**第 1 组：导入结果统计（批次 `I`，全集 `In_I`，`|In_I| = input_row_count`）**

```
G1  input_row_count
      = N_fail_import      -- 写入失败、未落库
      + N_quar             -- 落库、本批隔离
      + N_inserted         -- 落库、活性新增
      + N_updated          -- 命中既有活性行、内容变化、写入非伴生列
      + N_noop             -- 命中既有活性行、内容未变、只刷 last_batch_id
      + N_blocked          -- 记录级跳过（该行不动，其他行继续）
```

**第 2 组：回滚结果统计（回滚批次 `Rb`，被回滚批 `R`；`B = R.inserted_source_record_ids`，`N_new = |B|`）**

```
G2  (i)  N_new = N_quar + N_normal
    (ii) N_normal = N_rolled_back + N_blocked + N_fail_rb + N_noop
```

> **`N_noop` 的真实来源（必须写清，否则会被当成恒为 0 的占位项）**：`B` 内的行由 `R` 插入，回滚前若已失效，只可能来自**后续批次**的处置——① 后续批次判定源端消失 ⇒ `source_absent`；② 后续批次判定它是重复副本 ⇒ `duplicate_quarantine`（此情形进 `N_quar`、**不进** `N_noop`）。**所以 `N_noop` 与 `N_quar` 在同一次回滚里可以同时非零，这正是洞 4 的触发条件。**
> **`N_fail_import` 的硬边界**：失败行**没有** `source_record_id`（未落库 ⇒ 主键未生成）⇒ 它**不可能**出现在 `inserted_source_record_ids` 里。`|B|` **不得**把 `failed_count` 加进去再减回来——那会让 R1 的右式多减一次。

## F.6 回滚判定顺序（六步，命中即终止）

```
步骤 0（先判「本批作用集」= 本批的隔离结论）
    r.inactive_reason = 'duplicate_quarantine'                   ⇒ N_quar++        ─ 终止
步骤 1（此时才判历史失效）
    r.is_active = false OR r.inactive_reason IS NOT NULL         ⇒ N_noop++        ─ 终止
步骤 2（批次先后）
    r.last_batch_id ≠ R.batch_id                                 ⇒ N_blocked++     ─ 终止  台账 rollback_conflict
步骤 3（保护位，含 created_by='manual'）
    派生行任一：created_by='manual' / locked / manual_edited_fields 非空
                                                                 ⇒ N_blocked++     ─ 终止  台账 manual_edit_conflict
步骤 4（墓碑）
    派生行任一：merged_into_place_id IS NOT NULL                  ⇒ N_blocked++     ─ 终止  台账 rollback_conflict
步骤 5（写入失败）
    软撤 UPDATE 违反约束 / 事务中断                               ⇒ N_fail_rb++     ─ 终止  台账 import_row_error
步骤 6（其余）
                                                                 ⇒ N_rolled_back++
```

> ⛔ **步骤 0 必须在步骤 1 之前**——这是本版对 V0.2.2 §2.4.1 判定顺序的**唯一实质性修正**（原顺序把"作用集"放在第 1 步、把 `duplicate_quarantine` 放在第 2 步，导致隔离行在第 1 步就被 `is_active=false` 截走，`N_quar` 恒 0、`N_noop` 虚高）。
> ⛔ **步骤 0 的判据是 `inactive_reason` 的值，不是 `is_active` 的布尔值。** 任何以 `is_active = false` 打头的实现都会把 `duplicate_quarantine` 与 `source_absent` 混为一谈。
> ⛔ **步骤 1 必须在步骤 2 之前**：一行"已被后续批次置 `source_absent`"同时满足两者；先判批次先后会**凭空产生一条 `rollback_conflict`**。
> **回滚期记账粒度是「行」，导入期是「字段」——这是 R2 能否成立的前提**：导入期一条记录 3 个字段被挡 ⇒ 记 **3 行** `manual_edit_conflict`；回滚期一条记录不论被几个字段挡住 ⇒ 记 **1 行**（`field_name=''`，因为回滚是整行的一票否决）。**若不这么写死，R2 的 `count(台账) == N_blocked` 会在"一行多字段受保护"时直接破（3 ≠ 1）。**

## F.7 四条断言：R1 / R2 / R2b / R2c

| 断言 | 式 | 状态 |
|---|---|---|
| **R1** | `count(source_record WHERE inactive_in_batch_id=:R AND inactive_reason='batch_rolled_back') == N_normal − N_noop − N_blocked − N_fail_rb == (\|B\| − N_quar) − N_noop − blocked_count − failed_count` | **结构已验证；未验证**：需真实回滚批次（`U5`）。**R1 未被降级** |
| **R2** | `count(data_quality_issue WHERE batch_id=:Rb AND issue_type IN ('rollback_conflict','manual_edit_conflict')) == N_blocked` | **结构已验证**（1:1 的两个前提：命中即终止 ⇒ 一行最多一条；行级粒度 ⇒ 一行恰好一条）。`N_blocked` 由 R2b、`N_fail_rb` 由 R2c 分别处理 |
| **R2b** | `count(... WHERE batch_id=:Rb AND issue_type NOT IN ('rollback_conflict','manual_edit_conflict')) >= 0` | **补集**，恒真、**不做校验**；作用是**显式保留该集合**，防"为配平把质量问题归类成回滚问题" |
| **R2c** | `count(data_quality_issue WHERE batch_id=:Rb AND issue_type='import_row_error') == N_fail_rb` | **结构断言 + 未验证（U5）**：暂存原始 **12,631** 条台账中 `import_row_error` / `rollback_conflict` / `manual_edit_conflict` **三类全为 0 行**（入库口径为 12,831，这三类在两侧均 0）⇒ **无任何脚本可在暂存态证伪 R2c，也无任何真实回滚批次可代入** |

> ⛔ **R2 不得被 R2c 连带降级**：R2 的判据自洽性（1:1 的记账粒度）是可静态核对的，与被验数据无关；**R1/R2/R2b 与 R2c 必须分两行记录状态。**

## F.8 记录级跳过 + `blocked_count` +1（**不是 BLOCK_OP**）

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | 判定表第 3 / 4 / 5 行（`created_by='manual'` / `locked` / `manual_edited_fields` 非空）没有独立计数列；`import_batch` 无 `blocked_count`。 |

## F.10 STOP_AUTO：ordinal 跨版本无法一一对应时整组 `SKIP_UPDATE`

| 要素 | 内容 |
|---|---|
| **原设计（V2.1）** | 未规定 ordinal 跨版本变化的工程策略。V2.1 的立场是"重导后按新 ordinal 更新旧行"。 |
| **修改后（V2.1.1）** | 五种变化按"自动 / 停止"二分（见下表）；判据写死：**若 `\|old\| = \|new\|` 且 `\|old ∩ new\| < \|old\| − 1` ⇒ 有 ≥2 条同时变化 ⇒ 停止自动更新（STOP_AUTO）**。实现**不加新表、不加新列**：① 该组**整组 `SKIP_UPDATE`**；② 落 **1 条 `duplicate_external_id`** 台账（**复用既有类型，不新增枚举值**），`observed_value` 写 `old_multiset` / `new_multiset`，`notes` 写"ordinal 无法唯一对应，等待人工核验"；③ 每次导入重判，仍无法对应 ⇒ 再 `SKIP_UPDATE` + `occurrence_count += 1`。 |
| **原因** | ordinal 是**内容的函数**，不是身份。"ordinal 绑定了哪一行"**没有语义**；真正需要保护的是"`source_record_id` 绑定了哪份内容"。若机械按新 ordinal 更新，会出现"旧行的 id 挂到了另一份内容上"——**这是不可观测的数据损坏**（不报错、行数不变、内容看起来都合法）。 |
| **影响** | `source_record_id` / `created_from_source_record_id` / `duplicate_ordinal` 在 STOP_AUTO 期间**一律不动**；`raw_payload_json` **逐字保留**；台账复用 `duplicate_external_id`（`issue_type` 保持 19 值，**不新增枚举**）。 |
| **验证状态** | **结构已验证**（判据可判定、五表二分穷尽）。**未验证**：真实触发率（当前 **0 例**，需内容变更的源版本 = `U15`）；S3（`STOP_AUTO` 时该组 `content_hash` / ordinal 不变）。 |
| **出处** | V0.2.2 §2.5.1–§2.5.6；V0.2.1 §2.1.4a / G1-02（**引用时须同时标注 V0.2.2 §2.9 更正**）；IMPORT_RULES §8；CORE §4.7。 |

**五种变化（自动 / 停止二分）**

| # | 变化 | 可否自动对应 | 处置 |
|---:|---|---|---|
| ① | 同 hash 数量增减（`A,A` → `A,A,A`） | **可** | 自动：隔离数按子组内最小 ordinal 重算 |
| ② | 单条内容变化（`A,B` → `A,C`） | **可**（其余 hash 集未变） | 自动更新 |
| ③ | 组规模变化（1 组 → 2 行，或反向） | **可** | 自动；`ordinal=0` ↔ 1..n 的迁移按 F.2 判据 |
| ④ | **两条内容交换**（`A,B` → `B,A`，多重集相同） | **不可观测** | **显式接受该不可观测性，不构成台账事件；STOP_AUTO 有意不触发**（V0.2.2 裁定） |
| ⑤ | **≥2 条同时变化**（`A,B` → `C,D`） | **不可** | **STOP_AUTO**：整组 `SKIP_UPDATE` + 1 条台账 |

> **三条硬禁止**：① 不得仅因重排后 ordinal 不同而**静默更新旧行内容**；② 不得把原 `source_record_id` **自动绑定到另一条不同内容**的记录；③ 不得**删除**旧行。
> **两条硬保留**：① `raw_payload_json` 逐字保留；② `STOP_AUTO` 期间 `source_record_id` / `created_from_source_record_id` / `duplicate_ordinal` **一律不动**。
> ⚠️ **CIT-1 纪律**：凡引用 V0.2.1 §2.1.4a / G1-02 的"行序重排换绑"结论，**必须同时标注 V0.2.2 §2.9 的更正**，**不得单独转述旧理由**；且**不得**把任何逐次实测值写成断言。

## F.11 `should_write()`：唯一的写入判定（三处共用）

```
def should_write(entity, field, new_value) -> Decision:
    # 1. 墓碑优先于一切
    if entity.merged_into_place_id is not None:  return SKIP_ROW('merged_tombstone')
    # 2. 整行冻结
    if entity.locked:                            return SKIP_ROW('row_locked')
    # 3. 人工创建的行永不被导入改写
    if entity.created_by == 'manual':            return SKIP_ROW('manual_created')
    # 4. 字段级冻结
    if field in entity.manual_edited_fields:     return KEEP_MANUAL('field_edited')
    # 5. 身份列永不被导入器改写
    if field in ('place_id','location_id','name_id','source_record_id','created_at','created_by'):
        return KEEP('identity_column')
    return WRITE(new_value)
```

> **第 1 条必须排在最前**：`merged` 的行**不一定 `locked`**。若把 `merged` 判定放在 `locked` 之后，一个被合并的地点在源更新时会被直接改写墓碑行的字段，而 `merged_into_place_id` 保持不变 ⇒ 行仍是墓碑但内容已变，读路径 `COALESCE(merged_into_place_id, place_id)` 会把它解析到目标地点 ⇒ **用户看到目标地点的名字配上被改写的内容，没有任何报错**。
> **`should_write()` 必须被 upsert、回滚、人工解除保护后重导三处调用，且是同一份实现**（QA 检查项：8 份文档里 `should_write` / `decide` 的伪代码块出现次数必须为 1）。
